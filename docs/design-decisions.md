# Design decisions

Defaults chosen where the brief left room. Each can be revisited; the reason is stated so a change can be argued against it.

| # | Decision | Reason |
|---|---|---|
| 1 | Name `closebook`; installable package lives in `skills/closebook/` | Folder name must equal `name` (spec + Claude upload). The `skills/<name>/` layout also matches Claude Code plugins and leaves room for more skills. |
| 2 | Unit tests in repo-level `tests/`, not `scripts/tests/` | Keeps the uploadable package small and free of test files; Gemini uploads reject stray binary files such as `.pyc`. |
| 3 | Instruction files written in English; examples in both Chinese and English; replies follow the learner's language | Widest reach for an open-source repo; models follow English instructions reliably on all three platforms; bilingual examples show the language-following behaviour. |
| 4 | Calibration (confidence collection) and difficulty tuning are **always-on mechanics** that don't count against the "≤ 2 optional methods" cap | They cost no extra round trips and run inside the core loop; counting them would push out methods that need dedicated turns (Feynman, self-explanation). |
| 5 | Elaborative interrogation excluded for pure factual points, with the research caveat stated | Brief says so; Dunlosky et al. (2013) found some benefit for facts, so the reference says so honestly and routes "facts with a real why" through a secondary conceptual type. |
| 6 | Self-explanation allowed for procedural points; Feynman not | The brief defines self-explanation as "explain worked examples or code"; Feynman on procedures skips step-level reasoning. |
| 7 | New points start in box 0; the first pass moves them to box 1 (review tomorrow) | The first review is the most valuable; a same-session retest only shows short-term memory. |
| 8 | Only the **first scored attempt per point per day** can promote; failures always demote | A session retests the same point several times; letting each success promote would push freshly failed items out to weeks. |
| 9 | Hint policy: correct with hint 2 = fuzzy; anything after hint 3 = fail | Hint 3 shows the answer, so nothing was retrieved; hint 2 gives the structure, so recall was partial. |
| 10 | `verify_known` pass → box 2 (3 days), status `skipped_known` | Skipped content still gets a cheap check soon, without wasting tomorrow's review. |
| 11 | High-confidence error = `incorrect` with confidence 3; cleared only by a promoting pass on a later day | Matches "高信心答错" literally; partial answers at confidence 3 are fuzzy, not confident errors. |
| 12 | Exam date caps `next_review` at the day before the exam | Every point gets a last review before the exam without changing the box rules. |
| 13 | Schedule state is always **replayed from attempt history** on merge/import/record | Makes the tool deterministic and idempotent; chat-computed state that drifts from the rules is detected (`validate` warning) and fixed (`recompute`). |
| 14 | Compact export keeps **all** attempts (core fields only) rather than truncating history | Replay needs history; a 5-point topic after several sessions stays a few KB. |
| 15 | Contested points use `coherent / partly_coherent / incoherent` results, no confidence | No right answer exists; coherence still maps onto the scheduler (pass / fuzzy / fail). |
| 16 | `user_override` from the brief is stored as per-point `method_override_by_user` / `interaction_override_by_user` plus a top-level `user_overrides` log | Per-point fields answer "why was this point taught this way"; the log also covers flow-level overrides such as skipping a retest. |
| 17 | Session export format (`schemas/session-export.schema.json`) defined in phase 1 | The script must merge HTML-page exports now; the phase-2 page implements this format. |
| 18 | Validator is a small built-in JSON Schema subset; unknown fields are errors (`--lenient` makes them warnings) | Standard library only; strictness catches typos in model-written JSON, lenient mode avoids blocking a learner over an extra field. |
| 19 | Default platform level is 0 unless there is concrete evidence of more | Honesty is the top priority; claiming a UI that doesn't render is worse than plain text. |
| 20 | Interaction ids in the progress schema add `checklist` and `voice` to the 8 HTML ids | They appear in the interaction matrix but aren't HTML lesson components. |
| 21 | Subject-specific forms are new interaction types (`numeric`, `order_steps`, `cloze_passage`, `code_trace`, `terminal`, `graph`) plus a parameter-lab `simulation`; subject is a starting point, never a replacement for the knowledge-type fit | Keeps the decision chain intact: a history point that is contested still gets open argument. One form per subject would have hidden that. |
| 22 | Every subject form makes the learner commit first: a typed value, a prediction, or slider values with their own curve hidden until checked | Sliding until two curves overlap, or reading the answer off a visible graph, is guessing, not recall. |
| 23 | Formulas use a small built-in expression grammar, mirrored in `build_lesson.py`, instead of `eval` | Lesson data is model-written; nothing in it may run as code in the learner's browser. |
| 24 | The terminal accepts only listed commands, says so on the page, and lets the coach regrade a valid variant | A fake shell that pretends to run commands would mislead; an honest exact-match check is still useful retrieval practice. |
| 25 | Image hotspots and audio are left out | They need external images or microphone access; the page is offline and self-contained. |
| 26 | Two routes chosen by what the learner says: "teach me / I want to learn" → teach route (short chunks with checks, then the closed-book retests); "practise / quiz me / review" → practice route (diagnose first). A statement about prior knowledge beats the verb ("quiz me on Rust, never learned it" → teach). With no signal, the opening asks | Diagnosing a learner on material they've never seen produces only "don't know" and wastes their time; re-explaining material they already know skips the retrieval that makes it stick. The verb is a weaker signal than what they say they know. |
| 27 | Teaching comes in chunks of one idea (about 80–200 words, at most 3 per point), each followed by one check on a case the chunk didn't show; worked steps carry their reason; a missed check gets a different explanation, not a repeat | Novices learn more from explicit explanation with worked examples than from unguided problems, in learner-paced segments with a check after each step, and the support should fade (sources in `references/new-learning.md`). A check that repeats the chunk's sentence tests reading, not understanding. |
| 28 | Checks are recorded as phase `teach_check` and are unscored: no box change, not in the mistakes list. A point taught but not yet retested is due the next day | They happen seconds after the explanation, so a correct answer says little about memory. The closed-book retest is what schedules review; if the session ends before it, the retest moves to the next session instead of being lost. |
| 29 | Points on a learning path that aren't taught yet get status `planned`: never due, active on the first attempt | A path of ten points shouldn't produce ten "due" items on day one; reviews should only cover what was actually taught. |
| 30 | On the teach route, every point is taught (chunks with checks) before any retest; retests start with the point taught longest ago. Chosen by the maintainer on 2026-11-01 over retesting each point right after its teaching | A retest right after the explanation mostly measures working memory; with other points in between it takes more effort and shows what was retained. The one-question checks still catch misunderstandings before the next point builds on them. With a single point the retest follows directly. |
| 31 | The teach route has two paces, chosen by the learner once and stored as `settings.teach_pace`: `step` (check after every chunk; default from zero) and `section` (2–4 related points, at most ~8 chunks, explained in one reply, then one unscored check per point; no separate word limit, the chunk rules bound each point). A point missed twice on `section` drops to `step`. Retests are unchanged. The HTML page follows the same pace through the lesson's `teach_pace` and `sections` fields. Chosen by the maintainer on 2026-11-01 after finding one question per chunk too frequent | A check every two hundred words helps a novice but interrupts a learner who can follow a longer explanation (expertise reversal). Making the pace a stored preference keeps the small-step default for beginners, asks once instead of every session, and keeps the two parts that do the work: a missed check shrinks the step, and the scored retest still waits until all points are taught. |
| 32 | The agent's own interactive components come first in the renderer order: an inline widget facility (Codex/ChatGPT Visualize, Claude Code `show_widget`) that draws the question and sends the answer back to the chat, then a question tool with options when its host rules allow, then closebook MCP, the HTML page and text (`references/host-widgets.md`). With any renderer available the fit-matrix form is the default; the former "name the gain or use text" test is dropped. Chosen on 2026-11-01 after a tester on the Codex desktop app got text-only lessons | The hosts already ship widget facilities the skill never named, and its line "the ability to draw buttons proves nothing" made the model ignore them. Tapping an option or typing a number is the same retrieval as in text with less friction, so the component costs nothing pedagogically as long as a display is never counted as an answer. |
| 33 | Host widgets check keyed answers themselves ("Check answer" marks the choice, number, blanks or order on the spot and shows the explanation or worked steps); the result line goes to the chat only when the learner clicks "Next". Written answers still go to the chat for grading. Chosen by the maintainer on 2026-11-01 over grading every answer in chat | Instant feedback is the point of a component; a round trip through the chat for each answer makes the card slower than typing `B 2`. The HTML practice page has always graded with a stored key, so this matches it. The key is readable in the page source, which is accepted as the same honour system as the page: closed-book means the learner does not look. |
| 34 | Checking has three levels chosen by the learning task, not by the question count: one check per point (teach check, diagnostic, retest); after a section on the `section` pace, one **section review widget** with 3–5 questions stepped inside, graded there, one summary line back; for a day's or several days' points, a closed-book HTML **assessment page**. Teaching keeps coming first and uses the host's widgets for diagrams, step-throughs and explainers, with the words in the chat. Chosen by the maintainer on 2026-11-01 | One check per chunk interrupts; one message per section question is slower than typing `B 2`; a long review in chat is a stream of choices. Grouping by task keeps the small check where it catches a misconception early, gives the section its one card with instant feedback, and moves long assessments to a page built for them. Visuals in teaching make structure visible that sentences describe badly. |
| 35 | The practice page's **exam mode**: answers lock without feedback, the Mistakes tab is hidden, a countdown is optional, handing in (or the countdown) grades everything and shows a report (score, per-point results with weak points, wrong and unanswered items, every explanation). Attempts are `review`; the export carries `assessment` and each point's `section`. Training mode (`review`) is unchanged. Chosen on 2026-11-01 | A daily or cumulative assessment is a different act from practice: feedback after each answer would turn it into training and leak the pattern of the remaining questions. One hand-in keeps the closed-book promise, and the report tells the learner and the coach where to go next. |
| 36 | One upload ZIP for every chat app (claude.ai, ChatGPT, Gemini Apps): it leaves out `agents/openai.yaml` and `assets/lesson-template.html`; directory installs (Codex CLI/IDE, Claude Code, Gemini CLI, Hermes) copy the full `skills/closebook`. Chosen by the maintainer on 2026-11-01 over per-platform ZIPs | Gemini refuses `.yaml` uploads and ChatGPT's skill scan refuses any JavaScript (verified by narrowing on 2026-11-01), so no single package can carry both files and still upload everywhere. Hiding the page script inside Python would pass the scan by evasion and was rejected. The template is only usable where files can be opened in a browser, which the directory installs cover. |
