# MCP 与教学规则改进验证

日期：2026-11-01。范围：MCP `0.3.0`、skill 文档与评测。行为审计时，skill 元数据版本为 `0.2.0`；发布 [v0.3.0](https://github.com/sheepxux/closebook/releases/tag/v0.3.0) 时仅将版本元数据升为 `0.3.0`，未再改动受测教学规则或 MCP 实现。各轮受测快照及其摘要保持原样。skill 与 MCP 仍独立编号；历史 v0.2.0 与本次 v0.3.0 的 skill ZIP 均不包含单独配置的 MCP 服务。

本报告与此前的[练习页验证报告](validation-report.md)分开记录。本地审计期间没有重跑 HTML 浏览器测试，也没有把旧版本的桌面点击算作新版验收；随后发布验证在 GitHub Actions 上运行了完整套件，结果见下文。

## 已实现的改进

| 项目 | 实现与证据 |
|---|---|
| 内置能力优先 | 完整规则集中在 `interaction-fit.md`；依实际能力选择，与 agent 品牌无关。明确要求 MCP 时遵从；禁止把澄清或审批工具当测验，也不能为使用组件把开放题改成选择题。新增用例 29–34。 |
| 中英文界面 | 三个入口均支持 `locale`；显式交流语言优先于宿主语言，再以内容检测兜底。按钮、错误、可访问性标签、备用文本与回传消息一致。中文用户学英语仍可使用中文界面。 |
| 可靠启动 | 缺少、过期或损坏的构建产物会自动重建；内容指纹覆盖源码与依赖锁文件，避免旧文件时间戳造成漏更新。构建消息只写 stderr。预构建部署无需加载开发构建工具；HTTP 构建失败时不会先返回健康状态。 |
| 体积 | 自包含 HTML 从 621,848 字节降为 372,316 字节，减少约 40.1%。裁剪的是未使用的 Zod 错误翻译，保留完整协议、校验代码及中英文；未修改安装依赖。 |
| 检查入口 | `python3 tools/check.py` 统一 Python、打包与 MCP 检查；完整检查把任何跳过视为失败。GitHub Actions 配置安装浏览器并执行同一命令。 |
| 文档与命名 | MCP 包名改为 `closebook-mcp`；保留兼容的 `closebook_card` 注册名。清除本机开发记录，同步安装说明与各平台适配文档。四处可复制的英文安装提示词一致。 |

## 行为评测

使用已认证的 Codex CLI，模型 `gpt-6-astra`、推理设置 `ultra`。运行器只获得不含 `evals/` 的 skill 快照、场景及附件，不获得期望答案；另一个独立评分进程按每项期望引用证据。

当前套件为 **34 个用例、155 项期望**：原有 28 个用例按本次快照计 131 项，新 6 个用例共 24 项。历史报告保留其当时的统计，不替换为本次数字。

| 轮次 | 范围 | 原始评分结果 |
|---|---|---|
| 首轮 | 全部 34 例均完成回答 | 33 例完成评分，145/151；用例 14 的评分进程超时 |
| 超时补评分 | 使用同一份用例 14 回答，仅重新评分 | 4/4；首轮评分合计 149/155 |

原始回答、评分和补充证据见[本轮记录](eval-results/2026-11-01/mcp-hardening/README.md)。首轮与定向修复使用不同的源码快照，其内容摘要分别保留。最后三例有一次会话切换导致的中断，没有完整回答，未计入评分；保留中断说明后另起一轮。

### 首轮发现与修复

- **7：复习第一题旁又问时间。** 明确时间未知时使用已有或默认题量，不在首题追加问卷；7、8 的定向重测通过。
- **12：没有记录用户坚持选择的题型。** 增加纯聊天中的可见会话记录，并在导出时保留。首次修改后，11、12 仍出现过早视为用户覆盖选择或重复劝告的问题；进一步明确只有已解释过取舍后继续坚持才属于覆盖选择，最终 9/9。
- **24：大纲未明确其余内容留到后续课程。** 增加明确的范围说明，重测通过。
- **26：Rust 所有权讲解只用变量故事，缺少实际代码。** 编程操作必须先给最小真实代码，再讲规则；23、24、26 的最终定向重测全部通过。

### 两处评分需要补充证据

**用例 4**：原评分将图中的“B 此时掌握的证据：？”与结尾“B 能确定 A 已经收到了起点 700 吗？”视为两个问题，给出 3/4。独立语义复核认为一个完整回答即可同时完成，属于同一个推理任务，复核为 4/4；同时保留问句呈现有歧义的意见。原评分没有覆盖或删除。

**用例 22**：原评分进程不能调用工具，因未亲自运行验证器，把“JSON 通过验证”判为未验证。对首轮及修复轮的原始 JSON 均另外真实执行 `progress_tool.py validate`，结果有效，无错误或警告。这是机器补充证据，不把原评分伪写为通过。

这些结果证明受测模型在指定场景中的行为，不证明每个 agent 平台都支持某种内置界面；单次试验也不保证以后永不出错。各轮结果不可合并宣传成“最终版本一次完整 34 题全绿”。

## 真实客户端验收（2026-11-01）

用户明确确认已刷新 `closebook_card`，随后在 Codex 桌面逐张操作当前 `learning-card-v5` 卡片。七种形式均收到由 MCP App 发回同一聊天的真实消息，共 9 条（排序 3 条）。没有模拟用户点击，没有把演示作答写入学习进度。

原始消息和确认记录见[桌面验收数据](eval-results/2026-11-01/mcp-hardening/supplemental/desktop-acceptance-live.json)。表中的“通过”仅指所述提交路径；不代表该组件的每个按钮和所有异常分支都已在桌面测试。

| 卡片 | 实际观察 | 结果 |
|---|---|---|
| 知识讲解 | 收到“继续练习”事件；不记为答对或掌握 | 该路径通过 |
| 选择题 | 英文卡片返回 B（15 cm²）与信心 3；回传标签为英文，聊天继续用中文 | 回传通过 |
| 简答 | 两行中英文、×、÷ 和换行均传回；用户多复制的一段说明也保留 | 回传通过 |
| 数值题 | `1/2`、`m²`、`1 × 1 ÷ 2 = 1/2` 分别传回 | 回传通过 |
| 填空 | 三个空位 ID 与值对应；`hasn’t seen` 中 U+2019 弯撇号保留 | 回传通过 |
| 排序 | 前两次未得到要求的最终顺序；第三次两项补检返回 `one → two`，文字对应“数字 1 → 数字 2” | 最终顺序与回传补检通过 |
| 回忆卡 | 原文“低乘高除2”传回，没有自动改字；用户确认参考答案提交前不可见、提交后才出现 | 回传和翻面时序通过 |

**排序差异保留原始记录。** 首次要求 A→B→C，返回 C→D→B；用户表示没留意提交前的画面，因此无法判断实际操作。第二次要求先选 A→C→B，再将 B 上移，仍返回 A→C→B；用户明确回复“哦哦，我点错了”。这两次没有确立组件故障，也没有被反向改写为通过。

第三次缩成两个数字：要求先选 2、再选 1，将 1 上移，确认画面后提交。实际收到 `one → two`，文字顺序为数字 1、数字 2，与要求的最终顺序一致，因此该补检通过。证据是用户操作后的真实回传；没有独立的点击事件轨迹或录屏，不扩大为所有移动、移回按钮均已实测。

相同数据的 [DOM 定向核查](eval-results/2026-11-01/mcp-hardening/supplemental/ordering-dom-recheck.json) 已执行：选择 A→C→B，点击 B 上移一次，界面状态和提交消息均变为 A→B→C。该检查没有操作真实浏览器或 Codex 应用，不替代桌面补检。

本次没有独立观察屏幕，因此不宣称完成新版主题、所有双语标签和布局的视觉审查；下移、移回、不会、失败恢复等其他分支仍主要由自动测试覆盖。Claude、Hermes、Gemini 等客户端尚未实测。HTML 浏览器测试已在后续发布前 CI 中通过，不能据此推断其他客户端的 MCP 界面已验证。
